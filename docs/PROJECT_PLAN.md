# Ravenfjord: Project Plan

Battleship reimagined as a Viking naval strategy game, built as a Cognition Strategic Account
Executive technical challenge. This document holds the requirements, the rules specification,
the design and architecture decisions, and the milestones. It is updated as decisions change.

**Product-owner decisions (recorded):**

- The title is **RAVENFJORD**. Instructions and narrative text are Norse-themed. Button labels stay plainly functional.
- Milestone 1 ships as 3 sequential pull requests (scaffold, rules engine, themed UI), each merged only after CI passes.
- Styling uses plain CSS with design tokens (no Tailwind).
- The assumptions in section 9 are confirmed. There's no separate title screen: the game opens on fleet placement.

## 1. Project understanding

**Assignment deliverables:** a Battleship game you can play against an AI at a public URL, a public GitHub repo, and a debugging report covering real bugs (repro, root cause, fix, verification).

**Product vision:** standard Battleship rules presented as a Viking naval campaign, with a premium historical-strategy look ("Valhalla meets Battleship"). The atmosphere comes from cold Nordic seas, mist, fjords, wooden longships, and bronze and iron trim. The look is cinematic but the play stays simple and fast. The theme affects only presentation, ship names, and narrative wording. It never changes the rules.

**Gameplay rules:**

- Two 10x10 boards. One human plays against the computer.
- Fleet: Great Longship (5), Dragonship (4), War Longship (3), Raider (3), Scout Ship (2).
- Ships are horizontal or vertical, stay in bounds, and can't overlap. Ships may touch.
- The human places ships manually or with auto-place. The computer's fleet is placed randomly in valid positions.
- Turns strictly alternate, one shot each. A hit doesn't grant an extra turn. No square can be fired on twice.
- The UI shows hits, misses, sinkings, ships remaining, and whose turn it is. Enemy ships stay hidden until gameplay legitimately reveals them.
- The AI sees only the results of its own earlier shots.
- The game ends the moment a fleet is fully sunk. Restart is always easy to reach.
- Out of scope: multiplayer, accounts, payments, databases, and LLM-driven AI.

## Game rules specification

This section is the authoritative definition of every game state and action. The engine
(`src/engine/game.ts`) implements it as a pure reducer, and each rule below has at least one unit test.

### Constants

- Board: 10 columns (A–J) × 10 rows (1–10). Internally `{ row: 0–9, col: 0–9 }`.
- Fleet (same for both sides):

| ID              | Name           | Length |
| --------------- | -------------- | ------ |
| `greatLongship` | Great Longship | 5      |
| `dragonship`    | Dragonship     | 4      |
| `warLongship`   | War Longship   | 3      |
| `raider`        | Raider         | 3      |
| `scoutShip`     | Scout Ship     | 2      |

### State

| Field                               | Meaning                                                                            |
| ----------------------------------- | ---------------------------------------------------------------------------------- |
| `gameId`                            | Increments on every new game. Used to discard stale (delayed) computer moves.      |
| `phase`                             | `placement` → `battle` → `gameOver`                                                |
| `turn`                              | `player` or `computer`. Meaningful only during `battle`.                           |
| `boards.player` / `boards.computer` | Each holds that side's ship placements and the shots that side has _received_.     |
| `winner`                            | `null` until `gameOver`, then `player` or `computer`.                              |
| `log`                               | Ordered list of structured events (battle start, miss, hit, sunk, victory/defeat). |
| `rngState`                          | Seeded random state, so games are fully reproducible from a seed.                  |

### Placement rules

- A ship occupies `length` consecutive cells from its **origin** (the bow): rightward if horizontal, downward if vertical.
- Every cell must be on the board.
- No cell may be shared with another ship. **Touching (adjacent) ships are allowed.**
- Each ship can be placed at most once. To move a ship, remove it and place it again.
- The computer's fleet is generated by the same validation rules (random valid placement) when the game is created.

### Actions

Any action whose preconditions fail is **rejected**: the reducer returns the exact same state object, and nothing changes (no turn lost, no log entry).

| Action                     | Preconditions                                                                  | Effect                                                                                                                                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `PLACE_SHIP { placement }` | phase = `placement`; ship not already placed; in bounds; no overlap            | Ship added to the player's board                                                                                                                                                                             |
| `REMOVE_SHIP { shipId }`   | phase = `placement`; ship is placed                                            | Ship removed from the player's board                                                                                                                                                                         |
| `AUTO_PLACE`               | phase = `placement`                                                            | Player's fleet replaced by a random valid fleet of all 5 ships                                                                                                                                               |
| `CLEAR_FLEET`              | phase = `placement`                                                            | All player ships removed                                                                                                                                                                                     |
| `START_BATTLE`             | phase = `placement`; all 5 ships placed                                        | phase → `battle`, turn → `player`, "battle start" logged                                                                                                                                                     |
| `PLAYER_FIRE { coord }`    | phase = `battle`; turn = `player`; coord in bounds; coord not already fired on | Shot resolved on the computer's board (miss / hit / hit-and-sunk) and logged. If the computer's fleet is now fully sunk: phase → `gameOver`, winner = `player`. Otherwise turn → `computer`.                 |
| `COMPUTER_FIRE { gameId }` | phase = `battle`; turn = `computer`; `gameId` matches the current game         | AI picks a target from its targeting view only; shot resolved on the player's board and logged. If the player's fleet is now fully sunk: phase → `gameOver`, winner = `computer`. Otherwise turn → `player`. |
| `NEW_GAME`                 | any phase                                                                      | Fresh game: `gameId` + 1, phase → `placement`, player board empty, computer fleet re-randomized, no shots, empty log, no winner                                                                              |

### Shot resolution

- **Miss:** no ship occupies the cell.
- **Hit:** a ship occupies the cell.
- **Sunk:** the hit was on the last un-hit cell of that ship. The sunk ship's class is announced and its full position is revealed to the attacker.
- A hit **never** grants an extra turn.
- The game ends **immediately** when the last ship of a fleet sinks. No further shots are accepted from either side.

### Information and fairness

- The player sees their own ships, and on the enemy board only their own shots' outcomes plus fully revealed sunk ships.
- Enemy ship positions are not rendered in the page until legitimately revealed (sunk, or game over).
- The computer receives only a `TargetingView`: per-cell `unknown | miss | hit | sunk` for its own past shots, plus the lengths of the player's ships not yet sunk. Ship coordinates are not part of that type.
- The default `huntTargetAI` follows unresolved hit runs, then checks adjacent unknown cells; when hunting, it targets the shortest remaining ship's parity and falls back to any unknown cell if needed.
- Sunk cells are excluded from unresolved hits, so sinking one ship returns the AI to hunting while other unresolved hits remain targets.
- The human always fires first.

### UI-only conventions

- Clicking an already-fired square does nothing (the square is disabled), and no turn is consumed.
- The computer's move is shown after a short delay (~600 ms) with input locked. A move scheduled for an old game is discarded via `gameId`.
- New Battle asks for confirmation if a battle is in progress.
- Refreshing the page starts a new game (no persistence).

### Key design choices

1. **The engine is pure TypeScript with no React imports.** Every rule is a pure function, `(state, action) → newState`. The UI just renders state and dispatches actions through `useReducer`. _Why it matters:_ every rule can be unit-tested without a browser, and bugs can be traced to either "rules" or "display."
2. **No-cheating guarantee enforced by types.** The AI function signature is `chooseTarget(view: TargetingView, rng) → Coord`. `TargetingView` contains only a 10x10 grid of `unknown | miss | hit | sunk` plus the lengths of ships not yet sunk (standard public info). Ship coordinates aren't present in that type, so the AI can't cheat even by accident. A unit test also confirms that the view is identical for two different hidden fleets with the same shot history.
3. **Seeded random number generator (RNG).** All randomness (AI placement, AI shots, auto-place) goes through an injectable seeded RNG. Tests are deterministic and any bug can be replayed exactly. In non-production builds, `?seed=123` fixes a game for E2E tests. That parameter is **disabled in the production build**, so players can't replay a known enemy layout.
4. **Ships are rendered as cells in the same CSS Grid as the board.** A ship is a grid item spanning `grid-column: 3 / span 4` and so on, so it lines up with the cells by construction, at every screen size. This addresses the most likely visual bug: sprites drifting out of alignment.
5. **The computer's turn has a short delay (~600 ms) with input locked.** It reads as a turn instead of an instant flicker. The timer is tied to a game ID, so a pending AI shot can't land in a newly restarted game. That stale-timer race is a classic React bug.

### Game state model (simplified)

```ts
type Phase = 'placement' | 'battle' | 'gameOver';
interface GameState {
  gameId: number; // bumps on restart; guards stale AI timers
  phase: Phase;
  turn: 'player' | 'computer';
  player: { board: Board; shotsReceived: Shot[] };
  computer: { board: Board; shotsReceived: Shot[] };
  winner: 'player' | 'computer' | null;
  log: LogEntry[];
}
```

Actions: `PLACE_SHIP`, `REMOVE_SHIP`, `AUTO_PLACE`, `CLEAR_FLEET`, `START_BATTLE`, `PLAYER_FIRE`, `COMPUTER_FIRE`, `NEW_GAME`. The reducer rejects illegal actions (wrong phase, wrong turn, repeat square, invalid placement) and returns state unchanged. Illegal moves are impossible at the rules level, not just disabled in the UI.

## 4. Proposed user experience

**Screen flow:** Fleet placement → Battle → Victory/Defeat overlay → (New Battle) → Placement.

1. **No separate title screen (decided).** The game opens straight onto fleet placement under the RAVENFJORD header, which carries the wordmark and flavor line ("Muster your longships. Claim the northern seas.").
2. **Fleet placement ("Muster the Fleet"):**
   - On the left is the **dock**: the five ships as cards with silhouette, name, and length. Pick one to select it.
   - On the board, hovering shows a **ghost preview** of the selected ship. The tint is pale green if valid and red if invalid, and the reason is shown ("Out of bounds" / "Overlaps Dragonship").
   - Click to place. The clicked cell is the bow (left end when horizontal, top end when vertical).
   - **Rotate Ship** button or the `R` key toggles horizontal/vertical.
   - Click a placed ship to pick it back up.
   - **Auto-Place Fleet** fills or reshuffles all five. **Clear** empties the board.
   - **Start Battle** stays disabled until all five ships are placed.
   - On mobile: tap a cell to place (no hover). An invalid tap shows the reason inline.
3. **Battle:**
   - **Enemy Waters** is the larger, primary board. Hovering shows a crosshair. Already-fired squares are disabled. **Your Fleet** is the smaller secondary board, showing your ships with damage.
   - **Turn banner** at the top: "Your command, choose a target" vs "The enemy takes aim…". The inactive board dims slightly.
   - **Fleet Status:** both fleets as rows of ship names with health pips. Your ships show exact damage. Enemy ships show only "afloat" or "sunk", plus the class name once sunk.
   - **Battle Log:** newest first, about 6–8 lines visible, scrollable. Examples: "Your fleet struck an enemy vessel at D7!", "Enemy attack missed at B2.", "Enemy Dragonship sunk!"
   - **Markers:** a miss is a pale ripple ring. A hit is an ember-orange burst with an X. A sunk ship shows its hull revealed and darkened with a red-ember outline. Markers differ by **shape and color**, so they still work for color-blind players.
   - **New Battle** is always available in the header. It asks for confirmation during a battle.
4. **Victory / Defeat overlay:**
   - Victory: "VICTORY — The enemy fleet has fallen." Bronze knotwork frame, shield emblem, stats (turns, shots, hits, accuracy %).
   - Defeat: "DEFEAT — Your fleet rests beneath the waves." Cooler, darker treatment. The surviving enemy ships are revealed on the board, which is legitimate once the game is over.
   - **New Battle** button returns to placement.

**Terminology (decided):** headings, instructions, status text, and the battle log use Norse/Viking language wherever possible. **Button labels stay plainly functional** ("Start Battle", "Rotate Ship", "Auto-Place Fleet", "New Battle"), so nobody has to guess what a control does.

## 6. Visual implementation tradeoffs

| Decision  | Chosen                                                                             | Alternative rejected                         | Reason                                                                                                                                |
| --------- | ---------------------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Rendering | DOM + CSS Grid + SVG                                                               | Canvas / PixiJS / Three.js                   | Accessible (real buttons), testable with Playwright selectors, no rendering engine to debug, and plenty fast for 200 cells            |
| Ship art  | Hand-built SVG components                                                          | Raster images / AI-generated art             | Sharp at any size, rotation and theming are trivial, a few KB each, clearly original (no licensing question)                          |
| Textures  | CSS gradients (+ optionally one small locally bundled noise PNG < 30 KB)           | Large photo backgrounds                      | Fast load, nothing external, no licensing risk                                                                                        |
| Animation | CSS keyframes/transitions, `prefers-reduced-motion` respected                      | JS animation libraries (Framer Motion, GSAP) | Zero dependencies. GPU-friendly `transform`/`opacity` only. Effects never block input.                                                |
| Fonts     | 2 OFL families, self-hosted                                                        | Decorative "Viking" fonts                    | Decorative Norse fonts often have unclear licenses and poor legibility. Cinzel gives the carved gravitas without hurting readability. |
| Fidelity  | "Premium" through restraint: palette, typography, framing, a few signature details | Lots of ornament                             | Too much decoration makes the game look cheap and hides the grid. Your brief prioritizes clarity.                                     |

Honest caveat: hand-built SVG gets a strong, polished, stylized look, but not painterly AAA concept art. If you later want illustrated hero art for the title or victory screen, a properly licensed or commissioned raster image is the right way to add it. It should be an M2 decision.

## 8. Testing and debugging approach

**Unit tests (Vitest, engine):**

- Fleet: exactly 5 ships, lengths `[5,4,3,3,2]`, unique IDs, Viking names.
- Placement: valid horizontal and vertical. Rejects out of bounds on every edge (including the off-by-one at index 9/10). Rejects overlap. **Allows touching**. Rejects placing the same ship twice.
- Random placement: run 1,000 seeds, every fleet valid, all 17 cells occupied, no overlaps.
- Shots: miss, hit, sunk only when every cell is hit, correct ship ID reported. Repeat shot rejected with **no turn change**. Out-of-bounds coordinates rejected.
- Turns: player → computer → player. A hit does **not** grant another turn. Firing out of turn or in the wrong phase is rejected.
- Game over: the final hit sets the winner immediately. No further shots accepted after that, from either side.
- AI legality: over many full simulated games the AI never repeats a square or goes out of bounds, and always finishes within 100 shots.
- **AI no-cheating:** the `TargetingView` type has no ship fields, and the view for two different hidden fleets with identical shot outcomes is deep-equal. With the same seed and the same view, the AI picks the same move, which shows its decisions can't depend on hidden information.
- Reset: `NEW_GAME` returns a fresh placement phase. No shots, log, or winner carry over, and the computer fleet is re-randomized.

**Component tests (RTL):** a fired cell becomes disabled. Enemy ships aren't in the DOM before they're revealed (checked in the DOM itself, not just hidden with CSS, because a hidden `<div>` would still leak positions through dev tools). Start Battle is disabled until the fleet is complete. The turn banner text changes.

**Browser tests (Playwright, Chromium):**

- Both boards render 100 cells each, with coordinates.
- **Ship alignment:** each ship sprite's bounding box matches its cells' combined bounding box within 1 px, horizontal and vertical, at desktop and mobile viewports.
- Manual placement + rotate + pick-up. Auto-Place produces 5 ships.
- Fire at a square: a marker appears, the turn passes, the AI responds, and the log updates.
- Seeded full game to victory, then the overlay appears, then New Battle resets both boards.
- Responsive: 1440×900, 1024×768, 390×844. Controls stay visible, no horizontal scroll.
- Screenshots saved as CI artifacts for visual review.

**Manual QA:** I'll play several full games in the browser and record anything unexpected.

**Debugging report discipline:** only defects actually observed, each with a repro, expected vs actual, root cause, fix, a **regression test added**, and a commit/PR link. Risks that were prevented up front (e.g. the stale-timer guard) go in a separate "Risks mitigated by design" section, not in the bug list.

## 9. Assumptions and risks

**Assumptions (confirmed by the product owner):**

1. **The human always fires first.**
2. When an enemy ship is sunk, its **class name and full position are revealed** (standard "You sank my battleship" convention).
3. Ship anchor = clicked cell is the bow (top/left end).
4. Repeat-square clicks are simply ignored (cell disabled). No turn is lost and no message is needed.
5. On defeat, remaining enemy ships are revealed after the game ends.
6. No persistence: refreshing the page starts a new game. (Saving a game in progress to localStorage is easy to add later if wanted.)
7. Desktop-first. Mobile is fully functional, with boards stacked vertically.
8. English only, no sound in M1. Optional muted-by-default sound could be an M2 idea.

**Risks and mitigations:**

| Risk                                                                    | Mitigation                                                                             |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Ship art misaligned with cells across sizes and rotation                | Ships live in the same CSS Grid; Playwright bounding-box test                          |
| Stale AI timer firing after restart / double-firing in React StrictMode | `gameId` guard + reducer rejects out-of-turn shots; explicit tests                     |
| Hidden enemy ships leaking into the DOM                                 | Not rendered until revealed; RTL test asserts absence                                  |
| Two 10x10 boards cramped on phones                                      | Stacked layout, min cell size, enemy board first during battle                         |
| Theming hurting legibility                                              | Contrast checks on tokens; decoration kept outside the grid                            |
| GitHub Pages subpath breaking asset URLs                                | `base` set from env, Playwright run against the production build with that base        |
| Over-investing in visuals before rules are solid                        | Engine PR lands and is tested before any visual work                                   |
| VM has no Node installed                                                | I'll install Node 20 LTS and propose a blueprint update so future sessions start ready |

## 10. Milestone 1 acceptance criteria

M1 is complete when **all** of the following are true:

**Gameplay**

- [ ] Two 10x10 boards with A–J / 1–10 coordinates render.
- [ ] The fleet is exactly Great Longship 5, Dragonship 4, War Longship 3, Raider 3, Scout Ship 2.
- [ ] Manual placement works horizontally and vertically with a rotate control. Out-of-bounds and overlapping placements are blocked with a visible reason. Touching is allowed.
